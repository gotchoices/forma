# AGENTS.md — sheet-proton
Rules for AI agents working in this project.

## Scripts and outputs: cleanliness rules

The project will accumulate Python scripts and output files over time. To prevent clutter, follow these rules:

### Script organization

```
sheet-proton/
├── scripts/
│   ├── lib/                    # Shared utilities used by multiple scripts
│   │   └── geometry.py         # Profile + surface parameterization
│   ├── clover_profile.py       # 2D profile rendering
│   ├── corrugated_torus.py     # 3D surface rendering
│   ├── laplacian_spectrum.py   # Eigenvalue solver
│   └── ...
└── outputs/                    # All generated artifacts (PNG, CSV, etc.)
```

### The seven script rules

1. **One script per capability, not per experiment.** `clover_profile.py` handles all profile-rendering needs. If you want a variant (different colors, log-scale, etc.), add a CLI flag — don't create `clover_profile_v2.py`.

2. **Parameterize via argparse.** All scripts accept their parameters via command-line. No hard-coded values in script bodies (use defaults in `argparse.add_argument(..., default=...)`).

3. **Shared utilities go in `scripts/lib/`.** Profile parameterization, surface embedding, plotting style — all reused across scripts via imports from `lib/`.

4. **Augment, don't fork.** When a script needs new functionality, extend it (with flags, additional `--mode` options, new functions). Forking into `script_v2.py` is forbidden.

5. **No "scratch" scripts in scripts/.** If you need to test a one-off idea, do it in a notebook or a Python REPL session. The `scripts/` folder is for production-quality reusable code.

6. **Document each script's purpose at the top.** Module docstring should state: what it does, what inputs it takes, what outputs it produces. A new agent reading the file should know in 30 seconds whether the script applies to their task.

7. **Delete superseded scripts.** When a script is replaced by a better version, delete the old one. Don't leave commented-out code blocks or "// TODO: remove" notes.

### The four output rules

1. **Outputs/ is the only place artifacts land.** Plots, CSVs, JSON, anything generated — all goes to `outputs/`. Never write to the project root or to `scripts/`.

2. **Filenames encode parameters.** Use the form `<artifact>_<param1><value>_<param2><value>.ext`. Example: `profile_chi1.0.png`, `torus_chi0.5_R5.0.png`, `spectrum_eps0.2_chi1.0.csv`. This way the same script can produce many distinct outputs without overwriting.

3. **No nested directories in `outputs/`.** Keep it flat. Filenames alone should disambiguate.

4. **Outputs are disposable.** They can be regenerated by re-running scripts. If they get crufty, delete them; don't commit cruft to git.

### When the workflow needs to expand

If you genuinely need more structure than these rules allow (e.g., a second pipeline that diverges substantially from existing scripts), **stop and talk to the user before adding new top-level scripts or directories.** Don't proliferate.

### Reuse over re-invention

Before creating any new script, check `scripts/` and `scripts/lib/` for existing functionality. If 60% of what you need exists, extend the existing code; don't write a new script that duplicates 60% of an old one.

### Cross-project utility

If a utility function turns out to be useful beyond sheet-proton (e.g., generic torus visualization), promote it to a shared location after asking the user. Don't unilaterally relocate code.


## Workflow summary

1. Develop ideas in `work/*.md` (analytical exploration).
2. When numerics are needed, build/extend scripts in `scripts/`.
3. Generated artifacts go to `outputs/`.
4. When a work file's hypothesis converges, graduate to chapter-level prose.
5. Update `work/STATUS.md` as files move along the development arc.
